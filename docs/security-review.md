## กลุ่ม ก: ช่องโหว่จริง (ต้องแก้แม้มีล็อกอินแล้ว)

### ก1. แทรกคำสั่งใน PDF ทักษะ ทำให้เซิร์ฟเวอร์อ่านไฟล์ภายในหรือเรียก URL ภายใน

- **ความรุนแรง: สูง** (พิสูจน์แล้ว)
- **อยู่ที่:** `backend/main.py` บรรทัด 4488-4497 (ชื่อนักศึกษา / รหัส / ช่วงเวลา) และ 4562-4563 (ชื่อกิจกรรม / ทักษะ) ในฟังก์ชันสร้าง PDF ของ `GET /api/student/me/skills/export`

**ปัญหาคืออะไร**
ไลบรารีสร้าง PDF (ReportLab) อ่านข้อความแบบ "HTML ย่อส่วน" เช่น `<b>` คือตัวหนา `<img src="...">` คือใส่รูป ระบบเอาชื่อกิจกรรมและชื่อนักศึกษาใส่ลงไปตรง ๆ โดยไม่แปลงอักขระพิเศษก่อน ถ้าใครตั้งชื่อกิจกรรมเป็นคำสั่ง ไลบรารีจะทำตามคำสั่งนั้น

ชื่อกิจกรรมภายนอก (external activity) นักศึกษาเป็นคนพิมพ์เอง พอแอดมินอนุมัติ ชื่อนั้นจะไปอยู่ใน PDF

**ถ้าโดนจริงจะเกิดอะไร**
- ตั้งชื่อกิจกรรมเป็น `<img src="/path/รูปบนเซิร์ฟเวอร์">` แล้ว PDF ที่ได้จะมีรูปจากเครื่องเซิร์ฟเวอร์ติดมาด้วย (อ่านไฟล์รูปบนเซิร์ฟเวอร์ได้)
- ตั้งเป็น `<img src="http://เครื่องภายใน/...">` แล้วเซิร์ฟเวอร์จะไปเรียก URL นั้นเอง (เรียกว่า SSRF ใช้สำรวจหรือโจมตีเครื่องในเครือข่ายภายในที่คนนอกเข้าไม่ถึง)
- ชื่อที่มีแท็กไม่ครบ เช่น `<b>x` ทำให้สร้าง PDF ไม่ได้ (error 500) **สำหรับนักศึกษาทุกคนที่มีกิจกรรมนั้น** จนกว่าจะมีคนแก้ชื่อ

**พิสูจน์แล้ว:** ทดสอบทั้ง 3 แบบด้านบนได้ผลจริง (PDF มีรูปจากเครื่อง, เซิร์ฟเวอร์ทดสอบได้รับ request จากระบบ, export ได้ error 500)

**วิธีแก้ที่แนะนำ**
- ครอบทุกค่าที่มาจากผู้ใช้ด้วย `xml.sax.saxutils.escape()` ก่อนส่งให้ `Paragraph` (ชื่อ, รหัส, ชื่อกิจกรรม, ข้อความทักษะ, ชื่อช่วงเวลา)
- เสริม: ตั้ง `reportlab.rl_config.trustedSchemes = []` เพื่อไม่ให้ ReportLab โหลดรูปจาก URL เลย

หมายเหตุ: PDF Transcript (WeasyPrint, `backend/transcript_pdf.py`) **ปลอดภัย** เพราะเปิด autoescape ของ Jinja และจำกัดให้โหลดไฟล์ได้เฉพาะในโฟลเดอร์ backend

### ก2. แอดมินสาขาแก้ข้อมูลนักศึกษาสาขาอื่นได้ผ่านการ import ผู้เข้าร่วม

- **ความรุนแรง: สูง** (พิสูจน์แล้ว)
- **อยู่ที่:** `backend/main.py` บรรทัด 2604-2614 ใน `confirm_activity_participants` (`POST /api/activities/{id}/participants/import/confirm`) และตอนสร้างนักศึกษาใหม่ บรรทัด 2586-2603

**ปัญหาคืออะไร**
ตอนแอดมินแก้ข้อมูลนักศึกษาทีละคน (บรรทัด 2757-2766) ระบบตรวจว่านักศึกษาอยู่ในสาขาของแอดมินหรือไม่ แต่ตอน import ไฟล์รายชื่อผู้เข้าร่วม ระบบเอาชื่อ / อีเมล / คณะ / สาขาในไฟล์ไปทับข้อมูลนักศึกษาที่มีอยู่แล้ว **โดยไม่ตรวจสาขา**

**ถ้าโดนจริงจะเกิดอะไร**
- แอดมินสาขาเคมีใส่รหัสนักศึกษาสาขาคอมพิวเตอร์ในไฟล์ แล้วเปลี่ยนชื่อ อีเมล และสาขาเป็น "เคมี" ได้
- นักศึกษาคนนั้นจะย้ายมาอยู่ในความดูแลของแอดมินเคมี (เห็นประวัติกิจกรรม อนุมัติคำขอได้) และแอดมินสาขาเดิมจะมองไม่เห็นนักศึกษาคนนั้นอีก
- เมื่อมีล็อกอินจริงที่ใช้อีเมล การเปลี่ยนอีเมลของคนอื่นได้อาจกลายเป็นการยึดบัญชี

**พิสูจน์แล้ว:** แอดมินเคมีเปิดประวัตินักศึกษา CS ไม่ได้ (403) แต่หลัง import แล้วเปิดได้ (200) ส่วนแอดมิน CS กลับเปิดไม่ได้ และชื่อ / อีเมล / สาขาถูกเปลี่ยนจริง

**วิธีแก้ที่แนะนำ**
- นักศึกษาที่มีอยู่แล้ว: เรียก `ensure_can_access_student(admin, student)` ก่อนแก้ข้อมูล ถ้าเป็นนักศึกษาต่างสาขา (ซึ่งเข้าร่วมกิจกรรมข้ามสาขาได้) ให้เพิ่มเป็นผู้เข้าร่วมอย่างเดียว ไม่แก้ข้อมูลหลัก
- เรียก `ensure_can_assign_major(admin, major)` ทุกครั้งที่จะตั้งสาขา รวมถึงตอนสร้างนักศึกษาใหม่

### ก3. สร้างคำขอในนามนักศึกษาคนใดก็ได้ โดยไม่ต้องยืนยันตัวตน

- **ความรุนแรง: กลาง** (พิสูจน์แล้ว)
- **อยู่ที่:** `backend/main.py` บรรทัด 5066-5096 (`POST /api/requests`)

**ปัญหาคืออะไร**
endpoint นี้ไม่ตรวจเลยว่าใครเป็นคนส่ง ระบบเชื่อรหัสนักศึกษาและชื่อที่ส่งมาใน request ทันที ใช้ได้แม้ปิดโหมด bypass ทั้งหมด และ frontend ปัจจุบันไม่ได้เรียก endpoint นี้

**ถ้าโดนจริงจะเกิดอะไร**
- ใครก็ได้สร้างคำขอปลอมในชื่อนักศึกษาคนอื่น คำขอจะไปโผล่ในหน้าอนุมัติของแอดมินเหมือนของจริง

- การอนุมัติแค่เปลี่ยนสถานะคำขอ ไม่ได้เพิ่มคะแนนทักษะ ผลกระทบจึงจำกัด

**วิธีแก้ที่แนะนำ:** เพิ่ม `student: Student = Depends(get_current_student)` แล้วเอารหัส / ชื่อนักศึกษาจากตัวตนที่ยืนยันแล้ว ไม่รับจาก body หรือถ้าไม่มีหน้าไหนใช้ ให้ลบ endpoint นี้ออก

- **ความรุนแรง: ต่ำ** (พิสูจน์แล้ว)
- **อยู่ที่:** `backend/main.py` บรรทัด 2397-2419 (`/api/admin/students/lookup`), 2422-2453 (`/api/admin/students/search`), 2436 (สร้าง pattern ค้นหา)

**ปัญหาคืออะไร**

**วิธีแก้ที่แนะนำ:** สำหรับนักศึกษาต่างสาขา ส่งกลับแค่รหัสและชื่อ และ escape `\`, `%`, `_` ก่อนค้นหา (`ilike(pattern, escape="\\")`)

### ก10. ไม่จำกัดขนาด request โดยรวม

**ปัญหาคืออะไร:** ระบบจำกัดไฟล์หลักฐานที่ 5 MB ต่อไฟล์และ 10 ไฟล์ แต่การตรวจนี้เกิด **หลัง** เซิร์ฟเวอร์รับไฟล์ทั้งหมดเก็บลงดิสก์ชั่วคราวแล้ว และเกิดก่อนตรวจตัวตนด้วย

**ถ้าโดนจริงจะเกิดอะไร:** ส่งไฟล์ใหญ่มากพร้อมกันหลาย request ทำให้ดิสก์ชั่วคราวเต็ม

**วิธีแก้ที่แนะนำ:** จำกัดขนาด body ที่ reverse proxy (เช่น nginx `client_max_body_size`) หรือเพิ่ม middleware ตรวจ `Content-Length`

### ก11. ไม่มี security header

- **ความรุนแรง: ต่ำ** (จากการอ่านโค้ด)
- **อยู่ที่:** `frontend/nginx.conf` บรรทัด 1-19 (มีแค่ Cache-Control) และ backend ไม่ได้ตั้ง header เหล่านี้

**ปัญหาคืออะไร:** browser มีกลไกป้องกันเสริมที่ต้องเปิดผ่าน header แต่ระบบยังไม่ได้เปิด:
- `Content-Security-Policy`: จำกัดว่าหน้าเว็บโหลด script จากที่ไหนได้
- `X-Frame-Options` / `frame-ancestors`: กันเว็บอื่นเอาหน้าอนุมัติไปซ้อนหลอกให้กด (clickjacking)
- `X-Content-Type-Options: nosniff`: กัน browser เดาชนิดไฟล์เอง
- `Referrer-Policy`

**ถ้าโดนจริงจะเกิดอะไร:** ไม่ใช่ช่องโหว่โดยตรง แต่ถ้ามีช่องโหว่อื่น ความเสียหายจะมากกว่าที่ควร

**วิธีแก้ที่แนะนำ:** เพิ่ม `add_header ... always;` ใน nginx ซึ่งต้องใส่ซ้ำในทุก `location` เพราะแต่ละ location มี `add_header` ของตัวเองอยู่แล้ว และให้ backend ส่ง `X-Content-Type-Options: nosniff` (โดยเฉพาะตอนเปิดไฟล์หลักฐาน)

## กลุ่ม ข: เกิดเพราะยังไม่มีระบบล็อกอินจริง (รู้อยู่แล้ว)

ข้อเหล่านี้หายไปเมื่อทำระบบล็อกอินจริงที่ **ออก session หรือ token ฝั่งเซิร์ฟเวอร์** (เช่น cookie แบบ HttpOnly หรือ JWT ที่เซ็นแล้ว) และ backend อ่านตัวตนจาก session / token นั้น **ไม่อ่านจาก header ที่ browser ส่งมาเอง** ก่อนเปิดระบบให้คนอื่นเข้าถึง (เช่น ให้เพื่อนในวง Wi-Fi ทดสอบ หรือขึ้นเซิร์ฟเวอร์จริง) ต้องรู้ว่าข้อเหล่านี้ยังเปิดอยู่

### ข1. ปลอม header เป็นนักศึกษาคนใดก็ได้ และไม่มีสวิตช์ปิด

- **ความรุนแรง: สูง** ถ้าเปิดให้คนอื่นเข้าถึง (พิสูจน์แล้ว)
- **อยู่ที่:** `backend/main.py` บรรทัด 2887-2946 (`get_current_student`) และ `frontend/src/constants/currentStudent.js` บรรทัด 5 และ 13-62

**ปัญหาคืออะไร**
- backend รู้ว่าใครเป็นนักศึกษาจาก header `X-Student-Id` / `X-Student-Email` ที่ browser ส่งมา ส่ง `X-Student-Id` ของใครก็เป็นคนนั้นได้ทันที ไม่ต้องใช้รหัสผ่าน
- แก้ `studentSession` ใน localStorage ของ browser หรือใช้ curl ก็ได้เหมือนกัน
- ถ้าไม่มี session ใน localStorage, frontend ใช้รหัสจำลอง `670510659` ให้อัตโนมัติ (บรรทัด 5, 59-62)
- **ต่างจากฝั่งแอดมิน** ที่มีสวิตช์ `ADMIN_BYPASS_ENABLED` และค่าเริ่มต้นปิด ฝั่งนักศึกษา **ไม่มีสวิตช์ปิดเลย** ปิดโหมด bypass ของแอดมินแล้วก็ยังปลอมเป็นนักศึกษาได้
- ข้อดีที่มีอยู่: ถ้าส่งทั้งอีเมลและรหัสมาพร้อมกัน ระบบตรวจว่าตรงกัน (บรรทัด 2903-2909)

**ถ้าโดนจริงจะเกิดอะไร:** ดูกิจกรรม ทักษะ Transcript การแจ้งเตือนของนักศึกษาคนอื่น และส่ง / แก้ / ลบคำขอกิจกรรมภายนอกในนามคนอื่นได้

**วิธีแก้ที่แนะนำ**
- ระยะยาว: ทำล็อกอินจริงตามที่อธิบายด้านบน
- ทำได้ทันที: เพิ่มสวิตช์ เช่น `STUDENT_BYPASS_ENABLED` (ค่าเริ่มต้นปิด) แบบเดียวกับฝั่งแอดมิน ครอบการอ่าน header นี้

### ข2. รหัสนักศึกษาที่ไม่มีในระบบ ถูกสร้างเป็นนักศึกษาใหม่อัตโนมัติ

- **ความรุนแรง: กลาง** (พิสูจน์แล้ว)
- **อยู่ที่:** `backend/main.py` บรรทัด 2928-2944

**ปัญหาคืออะไร:** ส่ง `X-Student-Id` เป็นค่าอะไรก็ได้ที่ยังไม่มีในระบบ (แม้แต่ request แบบอ่านอย่างเดียว) ระบบจะเพิ่มนักศึกษาชื่อ "Demo Student" ลงฐานข้อมูลถาวร โดยไม่ตรวจรูปแบบรหัส

**ถ้าโดนจริงจะเกิดอะไร**
- ยิงซ้ำได้ไม่จำกัด ฐานข้อมูลเต็มไปด้วยนักศึกษาปลอม ซึ่งไปโผล่ในหน้ารายชื่อ ค้นหา และ dashboard ของแอดมิน
- รหัสยาวเกิน 30 ตัวทำให้ PostgreSQL error (500)
- ใช้คู่กับข้อ ก1 ได้ทันทีโดยไม่ต้องรอแอดมินอนุมัติ (ตั้งรหัสเป็น `<b>x` แล้ว export PDF พัง)
- รหัสอย่าง `<img src=x onerror=alert(1)>` ถูกบันทึกได้ แต่หน้าแอดมินไม่ใช้ `v-html` จึงแสดงเป็นข้อความธรรมดา (ไม่เกิด XSS)

**วิธีแก้ที่แนะนำ:** เลิกสร้างอัตโนมัติ หรือทำเฉพาะเมื่อเปิดสวิตช์ dev และตรวจรูปแบบรหัส (เช่น ตัวเลข 9 หลัก)

### ข3. ปลอม header เป็นแอดมินได้เมื่อเปิดโหมด bypass

- **ความรุนแรง: สูง เมื่อเปิดโหมด bypass** (พิสูจน์แล้ว)
- **อยู่ที่:** `backend/admin_auth.py` บรรทัด 40-43, `backend/main.py` บรรทัด 174-182 (`GET /api/admin/auth/bypass`)

**ปัญหาคืออะไร**
- เมื่อ `ADMIN_BYPASS_ENABLED=true` ใครส่ง header `X-Admin-Email` เป็นอีเมลแอดมินก็ได้สิทธิ์แอดมินนั้น
- `GET /api/admin/auth/bypass` แสดงรายชื่ออีเมลแอดมินทั้งหมดรวมถึงแอดมินกลางโดยไม่ต้องล็อกอิน

**สิ่งที่ทำไว้ดีแล้ว**
- ค่าเริ่มต้นเป็น **ปิด** (`compose.yml` และ `.env.example` ตั้ง `false` ค่าว่างก็ถือว่าปิด)
- ทดสอบแล้วว่าเมื่อปิด endpoint แอดมินทุกตัวตอบ 401 และไม่มีทางอื่นเข้าส่วนแอดมินได้

**วิธีแก้ที่แนะนำ:** ห้ามเปิด bypass บนเครื่องที่คนอื่นเข้าถึงได้ (ไฟล์ `.env` ของเครื่องพัฒนาตอนนี้ตั้ง `true` อยู่ ซึ่งใช้ได้เฉพาะเครื่องตัวเอง) และแทนด้วยล็อกอินจริง

### ข4. รหัสผ่านนักศึกษาทดสอบใช้ร่วมกัน และ login ไม่ได้ออก token

- **ความรุนแรง: กลาง**
- **อยู่ที่:** `backend/student_bypass.py` บรรทัด 11 (`STUDENT_MOCK_PASSWORD = "1234"`), `backend/main.py` บรรทัด 213-235

**ปัญหาคืออะไร:** ทุกบัญชีทดสอบใช้รหัส `1234` ซึ่งเขียนไว้ในโค้ด และ login สำเร็จแล้วระบบแค่ส่งข้อมูลนักศึกษากลับมา **ไม่ได้ออก token** ที่เซิร์ฟเวอร์ใช้ตรวจภายหลัง การ login จึงไม่ได้ป้องกันอะไรจริง (ดู ข1)

**วิธีแก้ที่แนะนำ:** แทนด้วยระบบล็อกอินจริง (เช่น CMU OAuth) ที่ออก session / token

## สิ่งที่ตรวจแล้วไม่พบปัญหา

| หัวข้อ | ผลการตรวจ |
|---|---|
| **SQL injection** | ไม่พบ ทุก query ใช้ SQLAlchemy ORM ส่งค่าแบบ parameter ไม่มี `text()`, raw SQL หรือการต่อ string เป็น SQL `order_by` ใช้คอลัมน์ตายตัว ไฟล์ `.sql` เป็น migration แบบคงที่ |
| **XSS** | ไม่พบ ไม่มี `v-html` / `innerHTML` / `eval` ใน frontend ข้อความจากผู้ใช้และข้อความ error แสดงผ่าน `{{ }}` (Vue escape ให้) ลิงก์ไฟล์หลักฐานเป็น blob URL ที่ระบบสร้างเอง `document.write` จุดเดียว (`StudentSkills.vue` บรรทัด 628) เขียนข้อความคงที่ |
| **Open redirect** | ไม่พบ หลัง login แอดมิน redirect ได้เฉพาะ path `/admin/...` (`AdminLogin.vue` บรรทัด 90-95) |
| **ชนิดไฟล์หลักฐาน** | ตรวจทั้งนามสกุลและเนื้อไฟล์จริง (magic bytes) รับเฉพาะ jpg / png / pdf ไม่เชื่อ content-type ที่ browser ส่งมา ไฟล์ SVG / HTML หรือ SVG ที่เปลี่ยนนามสกุลเป็น .png ถูกปฏิเสธ (`main.py` บรรทัด 2957-3011) |
| **ขนาดไฟล์หลักฐาน** | อ่านไม่เกิน 5 MB + 1 byte ต่อไฟล์ และไม่เกิน 10 ไฟล์ (`main.py` บรรทัด 2985, 3020-3031) แต่ดูข้อ ก10 |
| **ตั้งชื่อไฟล์เพื่อเข้าถึงนอกโฟลเดอร์ (path traversal)** | ไม่พบ ลองชื่อ `../../../evil.png`, `/etc/evil.png`, อักขระ NUL, ขึ้นบรรทัดใหม่ ไฟล์ถูกเก็บเป็นชื่อสุ่ม (`uuid4`) ในโฟลเดอร์ของคำขอเสมอ ชื่อเดิมผ่าน `Path(...).name` |
| **เปิดไฟล์หลักฐานของคนอื่น** | ระบบตรวจว่าไฟล์เป็นของคำขอนั้น และนักศึกษาที่ขอเป็นเจ้าของ (ส่งรหัสคนอื่นได้ 403) ไม่มีโฟลเดอร์ uploads ที่เปิดให้ดาวน์โหลดตรง ๆ แต่ปลอมตัวตนได้ (ดู ก6, ข1) |
| **Endpoint นักศึกษา (`/api/student/me/*`)** | เอาตัวตนจาก dependency เสมอ ไม่รับรหัสนักศึกษาจาก URL หรือ body การแก้ / ลบคำขอและการอ่านแจ้งเตือนตรวจความเป็นเจ้าของถูกต้อง |
| **Endpoint แอดมิน** | ทุกตัวมีการตรวจตัวตนแอดมิน dashboard / รายการคำขอ / การอนุมัติกรองตามสาขาถูกต้อง แอดมินสาขาส่ง `?major=` ของสาขาอื่นไม่ได้ (ยกเว้นข้อ ก2, ก5, ก7) |
